| 영역 | MVP 기능 명칭 | 설명 | 우선순위 |

| **상품 관리 (Catalog)** | 상품 마스터 등록/수정 | 구매할 상품 정보(원가, 공급가, 예상 배송비)를 체계적으로 입력하고 관리. | 1 |
| | 재고 연동 기초 | 특정 상품의 현재 재고 수량을 표시하고 주문 시 차감하는 기초 로직 구현. | 2 |
| **주문 처리 (Order)** | 주문 생성 및 상태 관리 | 고객으로부터 주문을 받고, 주문 상태(결제 대기 $\rightarrow$ 배송 중 $\rightarrow$ 완료)를 시스템이 자동 업데이트. | 1 |
| | 주문 상세 내역 조회 | 고객별로 과거 주문 내역과 현재 진행 상황을 확인할 수 있는 기능. | 2 |
| **고객 관계 (CRM)** | 사용자 인증 및 관리 | 회원가입, 로그인, 개인 정보 관리를 위한 기본적인 보안 구조 확립. | 1 |
| | 주문/고객 연동 | 특정 고객에게 연결된 주문 목록과 구매 이력을 한눈에 파악. | 2 |

#### 2. 기능별 필수 학습 지식 (Claude/코딩 지식)

위 MVP 기능을 실제로 구현하기 위해 '바이브코딩' 과정에서 반드시 숙지하고 코드로 옮겨야 할 핵심 개념들입니다. 추상적인 이론보다 **실제 코드 구조**에 초점을 맞춰 학습하세요.

| MVP 기능 | 필수 학습 지식 (핵심 키워드) | 왜 필요한가? (목표) |
| :--- | :--- | :--- |
| **상품 마스터 등록/수정** | **데이터베이스 설계 (ERD)**, 관계형 데이터베이스(SQL), ORM 기초 (예: SQLAlchemy/Django ORM), JSON/YAML 파일 처리. | 상품 정보의 무결성을 보장하고, 데이터를 효율적으로 저장 및 조회하기 위함. |
| **재고 연동 기초** | **트랜잭션 관리**, 동시성 제어(Concurrency Control), 상태 머신(State Machine) 설계. | 주문 시 재고가 중복 차감되는 오류를 방지하고, 시스템의 일관성을 유지하기 위함. |
| **주문 생성 및 상태 관리** | **API 설계 (RESTful)**, HTTP 상태 코드 이해, 비동기 처리 (Async/Await), 데이터 유효성 검사(Validation) 로직. | 외부 연동(결제, 배송 API)을 위한 표준화된 인터페이스를 구축하고 오류를 최소화하기 위함. |
| **주문 상세 내역 조회** | **데이터 필터링 및 쿼리 최적화**, 인덱스(Index)의 이해, 효율적인 데이터 검색 알고리즘. | 대량의 주문 데이터에서 필요한 정보를 지연 없이 빠르게 추출하기 위함. |
| **사용자 인증 및 관리** | **비밀번호 해싱 (Hashing)**, 세션/토큰 기반 인증(JWT), 입력값 Sanitization (보안 취약점 방지). | 고객 정보와 시스템 접근 권한을 안전하게 보호하기 위함. |

*   `markup_rate`: 마진율 (%)

*   **관계 변경:** `Product` $\to$ 1:N $\to$ `SKU` $\to$ N:1 $\to$ `Inventory`
*   **개선 속성:**
    *   `product_id`: 상품의 개념적 ID (예: "나이키 운동화")
    *   `sku`: 재고 관리 단위 ID (예: "NKY-WH-270") - **PK**

*   **필수 추가 필드:** `effective_start_date`, `effective_end_date` (시간 범위 정의)
*   **관계 변경:** `PricingRule` $\to$ N:M $\to$ `Product` / `Agent`
*   **개선 속성:**
    *   `rule_id`: 규칙 고유 ID.
    *   `product_id` (FK): 적용 상품.
    *   `agent_id` (FK): 원천 에이전트.
    *   `price_type`: 판매가, 원가, 마진율 등 (Enum 사용).
    *   `value`: 실제 금액 또는 비율 값.

*   **개선 속성:**
    *   `link_id`: PK.
    *   `product_id` (FK): 연결 상품.
    *   `source_url`: 원본 URL.
    *   `scraper_config`: 스크래핑 방법/설정 정보.
    *   **`metadata_json`**: JSONB 타입으로, 해당 링크에서 추출한 **모든 추가 속성** (예: 모델 번호, 소재지, 배송 정책 등)을 저장하여 추후 분석에 활용합니다.

### D. 트랜잭션 데이터 (`Order`, `TransactionLog`) 개선: 이벤트 소싱 패턴 도입
주문이나 재고 상태는 한 순간의 스냅샷이 아닙니다. '어떤 일이 왜 발생했는지' 기록하는 것이 중요합니다.

*   **추천 방식:** **Event Sourcing Pattern (사건 기반 아키텍처)**
*   `Order` 테이블을 단순한 최종 정보 저장소가 아닌, `Order_Events`와 같은 이벤트 로그의 집합으로 설계하는 것을 고려해야 합니다.

| 이벤트 예시 | 발생 시점 | 기록 내용 | 중요성 |
| :--- | :--- | :--- | :--- |
| `ORDER_CREATED` | 주문 접수 시 | 초기 결제 금액, 고객 정보 | 트랜잭션 시작점 |
| `PRICE_UPDATED` | 가격 정책 변경 시 | 이전가/신가격, 변경 사유 | 수익성 추적의 핵심 |
| `INVENTORY_ADJUSTED` | 재고 변동 발생 시 | 증감 수량, 원인 (판매/반품/입고) | 실시간 판매 관리 |

## 3. 요약 및 개발팀 참고 지침

1.  **데이터 무결성 우선:** 가장 중요한 것은 데이터의 '진실성'입니다. `Order`와 `PricingRule`은 단순한 관계가 아닌, **시간 축을 가진 버전 관리 시스템**으로 설계해야 합니다.
2.  **유연성과 확장성 확보:** 모든 외부 소스(Agent)의 비정형 데이터는 `JSONB` 타입을 활용하여 임시 저장소처럼 사용하고, 핵심적인 속성만 정규화된 컬럼에 매핑하세요.
3.  **Performance 최적화:** 트래픽이 폭증하는 로그(`TransactionLog`)나 대량의 상태 변화가 발생하는 테이블은 인덱싱 전략(특히 B-Tree와 GiST)을 사전에 설계해야 합니다.

## 📦 쿠팡 API 기반 주문/배송 관리 기능 구현 상세 분석

쿠팡 API를 통해 쇼핑몰 운영에 필요한 핵심 기능을 구현하기 위해서는 크게 **인증**, **주문 조회**, **재고/발송 상태 업데이트**, **반품/취소**의 세 가지 축으로 API를 설계해야 합니다.

### 1. 공통 사항: 인증 및 기본 구조

모든 API 호출은 보안을 위해 반드시 쿠팡에서 제공하는 인증 절차를 따라야 합니다.

*   **인증 방식:** 일반적으로 **Access Token** 기반의 OAuth 2.0 또는 API Key 인증 방식을 사용합니다.
    *   **필수 정보:** 애플리케이션 등록, Client ID, Client Secret 발급 및 Access Token 획득 과정이 선행되어야 합니다.
*   **데이터 흐름:** 요청(Request) $\rightarrow$ 쿠팡 서버 $\rightarrow$ 응답(Response)의 순서로 데이터가 오고 갑니다.

### 2. 기능별 API 엔드포인트 및 요구사항 상세 정리

| :--- | :--- | :--- | :--- | :--- |
| **신규 주문 생성** | 구매대행으로 들어온 주문 정보를 쿠팡 시스템에 등록 및 연동 준비 | `POST /orders` 또는 유사 엔드포인트 | 주문번호, 상품코드(ASIN), 수량, 판매자 정보 등 | 통합 솔루션에서 주문 발생 시, 해당 데이터를 API로 전송하여 쿠팡 내 주문 상태를 초기화하거나 연동 시작. |
| **주문 상세 조회** | 주문의 실시간 상태 및 상세 정보를 확인 | `GET /orders/{order_id}` | 주문번호 | 통합 솔루션에서 실시간 재고/배송 상태 추적을 위해 주기적으로 호출. |

#### B. 발송 대기 및 배송 중 (Shipping & Tracking) 관련

| 구분 | 목적 | 예상 엔드포인트 (예시) | 필수 요청 파라미터 (예시) | 데이터 처리 흐름 |
| :--- | :--- | :--- | :--- | :--- |
| **발송 정보 업데이트** | 주문이 발송 준비 상태로 변경되었음을 시스템에 알림 | `PUT /orders/{order_id}/status` | 신규 배송 상태 (예: '발송 대기') | 통합 솔루션에서 상품 포장 및 송장 발행 후, 해당 정보를 API로 전송하여 쿠팡 주문 상태를 업데이트. |
| **배송 중 추적** | 현재 물류 이동 상황을 실시간으로 확인 | `GET /shipments/{tracking_number}` | 운송장 번호 (Tracking Number) | 고객에게 배송 현황을 제공하기 위해 주기적으로 호출하여 상태 정보를 갱신. |

#### C. 배송 완료 (Delivery Complete) 관련

| 구분 | 목적 | 예상 엔드포인트 (예시) | 필수 요청 파라미터 (예시) | 데이터 처리 흐름 |
| :--- | :--- | :--- | :--- | :--- |
| **배송 완료 등록** | 실제 배송이 완료되었음을 시스템에 최종 보고 | `POST /orders/{order_id}/complete` | 주문번호, 완료일자, 실제 수령 정보 등 | 고객에게 최종 알림을 보내고, 통합 솔루션 내의 주문 상태를 '완료'로 확정. |

#### D. 반품 및 취소 (Return & Cancellation) 관련

| 구분 | 목적 | 예상 엔드포인트 (예시) | 필수 요청 파라미터 (예시) | 데이터 처리 흐름 |
| :--- | :--- | :--- | :--- | :--- |
| **반품 신청** | 고객의 반품 요청을 쿠팡 시스템에 접수 | `POST /returns` | 주문번호, 반품 사유, 반품 상품 정보 | 통합 솔루션에서 반품 요청이 발생하면, 해당 정보를 API로 전송하여 쿠팡 반품 프로세스를 시작. |
| **주문 취소** | 고객 또는 판매자 측의 주문을 취소 요청 | `POST /orders/{order_id}/cancel` | 주문번호, 취소 사유 | 통합 솔루션에서 취소 요청이 발생하면, API 호출 후 내부 시스템 상태를 '취소 요청 중'으로 변경하고 쿠팡 상태를 대기. |

개발팀에게 전달할 때 다음의 논리를 포함해야 합니다.

3.  **데이터 정규화:** 쿠팡에서 반환되는 데이터 필드명과 통합 솔루션의 데이터 모델 필드명을 일치시키는 **매핑 레이어(Mapping Layer)**를 반드시 설계해야 합니다.

1.  **상태 동기화의 중요성:** 주문, 배송, 반품 등 모든 상태 변경은 **양방향 동기화(Two-way Synchronization)**가 필수입니다. 통합 솔루션이 쿠팡 데이터를 업데이트하는 것뿐만 아니라, 쿠팡의 상태 변경을 실시간으로 구독해야 합니다.

3.  **데이터 정규화:** 쿠팡에서 반환되는 데이터 필드명과 통합 솔루션의 데이터 모델 필드명을 일치시키는 **매핑 레이어(Mapping Layer)**를 반드시 설계해야 합니다.

### 1. 기술 스택 학습 로드맵 비교 분석

| 학습 목표 영역 | 전통적 접근 (Legacy/Monolithic) | 최신 모범 사례 (Modern/Microservices) | 권장 학습 우선순위 |
| :--- | :--- | :--- | :--- |
| **핵심 언어/프레임워크** | Python (Django/Flask) 또는 PHP 기반의 단일 시스템 구축 | **Python (FastAPI/Django)** + 비동기 처리(Asyncio) 기반 마이크로서비스 아키텍처(MSA) | 1순위: Python 비동기 프로그래밍, API 설계 심화 |
| **데이터베이스** | 관계형 DB (MySQL, PostgreSQL) 단독 사용 | **Polyglot Persistence:** 트랜잭션 데이터는 RDB (PostgreSQL), 로그/캐싱은 NoSQL (Redis, MongoDB) 혼합 사용 | 2순위: RDB 정규화 및 NoSQL 데이터 모델 이해 |
| **API 연동** | RESTful API의 단순 호출 중심 | **GraphQL 또는 Event-Driven Architecture (EDA):** 비동기 이벤트 기반 통신(Kafka/RabbitMQ)을 통한 시스템 간 결합도 낮추기 | 3순위: OAuth2/JWT 인증 및 메시지 큐 설계 |
| **배포/인프라** | 자체 서버 구축 및 관리 | **컨테이너화 (Docker) + 오케스트레이션 (Kubernetes):** CI/CD 파이프라인 자동화 | 4순위: Docker, 기본적인 Kubernetes 개념 이해 |

### 2. 데이터 모델 설계 최신 모범 사례 비교 분석

데이터 모델은 시스템이 데이터를 얼마나 효율적으로 저장하고, 트랜잭션의 무결성을 보장하는지를 결정합니다. 통합 솔루션에서는 **'트랜잭션 안정성'**과 **'데이터 유연성'**을 동시에 확보해야 합니다.

| 설계 원칙 | 관계형 데이터베이스 (RDB) 기반 접근 | NoSQL/스키마리스 접근 | 통합 솔루션에 대한 적용 방안 |
| :--- | :--- | :--- | :--- |
| **정규화 수준** | 3차 정규형(3NF) 이상을 목표로, 데이터 중복 최소화 및 무결성 극대화. | 스키마 유연성을 확보하며, 관계를 애플리케이션 레벨에서 관리. | **하이브리드 접근:** 핵심 트랜잭션(주문, 재고)은 RDB로, 로그, 사용자 피드백 등 비정형 데이터는 NoSQL로 분리하여 저장. |
| **관계 정의** | 명시적인 외래 키(Foreign Key)를 사용하여 테이블 간의 엄격한 관계를 정의. | 임베딩(Embedding) 또는 참조(Reference) 방식을 사용하며, 쿼리 시점에 관계를 추론. | **중요 트랜잭션은 RDB로 고정**하고, 외부 API 데이터나 로그는 JSON 형태(NoSQL)로 저장하여 유연성을 확보. |
| **트랜잭션 안정성** | ACID 원칙을 보장하여 금융/재고 거래의 정확성 보장. | 분산 트랜잭션 처리가 복잡해지므로, 서비스 단위로 트랜잭션을 격리하는 방식 채택. | **핵심 데이터(주문 상태, 재고)는 RDB 내에서 ACID를 유지**하고, API 연동 데이터는 별도의 로그 테이블에 기록하여 이관 실패 시에도 시스템의 핵심 안정성을 보장. |

#### 💡 분석 요약 및 제언
1.  **모델 설계 전략:** 통합 솔루션은 **'핵심 비즈니스 로직(주문/재고)'을 RDB로 확고히 하고, '외부 연동 데이터(API 응답), 시스템 로그'는 NoSQL로 유연하게 관리하는 하이브리드 모델**이 가장 적합합니다.
2.  **데이터 흐름:** 쿠팡 API에서 들어오는 데이터는 시스템 내부의 **정규화된 데이터 모델에 맞춰 변환 및 매핑(Mapping)** 과정을 거쳐 저장되어야 합니다. 이 변환 로직이 솔루션의 핵심 품질을 결정합니다.
