통합 솔루션은 크게 **상품 관리**, **주문 처리**, **고객 관계** 세 가지 축으로 구성되어야 합니다.

| 영역 | MVP 기능 명칭 | 설명 | 우선순위 |
| :--- | :--- | :--- | :--- |
| **상품 관리 (Catalog)** | 상품 마스터 등록/수정 | 구매할 상품 정보(원가, 공급가, 예상 배송비)를 체계적으로 입력하고 관리. | 1 |
| | 재고 연동 기초 | 특정 상품의 현재 재고 수량을 표시하고 주문 시 차감하는 기초 로직 구현. | 2 |
| **주문 처리 (Order)** | 주문 생성 및 상태 관리 | 고객으로부터 주문을 받고, 주문 상태(결제 대기 $\rightarrow$ 배송 중 $\rightarrow$ 완료)를 시스템이 자동 업데이트. | 1 |
| | 주문 상세 내역 조회 | 고객별로 과거 주문 내역과 현재 진행 상황을 확인할 수 있는 기능. | 2 |
| **고객 관계 (CRM)** | 사용자 인증 및 관리 | 회원가입, 로그인, 개인 정보 관리를 위한 기본적인 보안 구조 확립. | 1 |
| | 주문/고객 연동 | 특정 고객에게 연결된 주문 목록과 구매 이력을 한눈에 파악. | 2 |

#### 2. 기능별 필수 학습 지식 (Claude/코딩 지식)

위 MVP 기능을 실제로 구현하기 위해 '바이브코딩' 과정에서 반드시 숙지하고 코드로 옮겨야 할 핵심 개념들입니다. 추상적인 이론보다 **실제 코드 구조**에 초점을 맞춰 학습하세요.

| MVP 기능 | 필수 학습 지식 (핵심 키워드) | 왜 필요한가? (목표) |
| :--- | :--- | :--- |
| **상품 마스터 등록/수정** | **데이터베이스 설계 (ERD)**, 관계형 데이터베이스(SQL), ORM 기초 (예: SQLAlchemy/Django ORM), JSON/YAML 파일 처리. | 상품 정보의 무결성을 보장하고, 데이터를 효율적으로 저장 및 조회하기 위함. |
| **재고 연동 기초** | **트랜잭션 관리**, 동시성 제어(Concurrency Control), 상태 머신(State Machine) 설계. | 주문 시 재고가 중복 차감되는 오류를 방지하고, 시스템의 일관성을 유지하기 위함. |
| **주문 생성 및 상태 관리** | **API 설계 (RESTful)**, HTTP 상태 코드 이해, 비동기 처리 (Async/Await), 데이터 유효성 검사(Validation) 로직. | 외부 연동(결제, 배송 API)을 위한 표준화된 인터페이스를 구축하고 오류를 최소화하기 위함. |
| **주문 상세 내역 조회** | **데이터 필터링 및 쿼리 최적화**, 인덱스(Index)의 이해, 효율적인 데이터 검색 알고리즘. | 대량의 주문 데이터에서 필요한 정보를 지연 없이 빠르게 추출하기 위함. |
| **사용자 인증 및 관리** | **비밀번호 해싱 (Hashing)**, 세션/토큰 기반 인증(JWT), 입력값 Sanitization (보안 취약점 방지). | 고객 정보와 시스템 접근 권한을 안전하게 보호하기 위함. |

*   `markup_rate`: 마진율 (%)
*   `fee_structure`: 수수료 구조 정의

### A. `Product` 테이블 개선: SKU와 변형 관리

*   **필수 추가 엔티티:** `SKU (Stock Keeping Unit)`
*   **관계 변경:** `Product` $\to$ 1:N $\to$ `SKU` $\to$ N:1 $\to$ `Inventory`
*   **개선 속성:**
    *   `product_id`: 상품의 개념적 ID (예: "나이키 운동화")
    *   `sku`: 재고 관리 단위 ID (예: "NKY-WH-270") - **PK**
    *   `variation_attributes`: JSONB 타입. 색상, 사이즈 등 변형 속성을 기록.

### B. `PricingRule` 테이블 개선: 시간 및 소스 기반 가격 정책

*   **필수 추가 필드:** `effective_start_date`, `effective_end_date` (시간 범위 정의)
*   **관계 변경:** `PricingRule` $\to$ N:M $\to$ `Product` / `Agent`
*   **개선 속성:**
    *   `rule_id`: 규칙 고유 ID.
    *   `product_id` (FK): 적용 상품.
    *   `agent_id` (FK): 원천 에이전트.
    *   `price_type`: 판매가, 원가, 마진율 등 (Enum 사용).
    *   `value`: 실제 금액 또는 비율 값.

*   **개선 속성:**
    *   `link_id`: PK.
    *   `product_id` (FK): 연결 상품.
    *   `source_url`: 원본 URL.
    *   `scraper_config`: 스크래핑 방법/설정 정보.
    *   **`metadata_json`**: JSONB 타입으로, 해당 링크에서 추출한 **모든 추가 속성** (예: 모델 번호, 소재지, 배송 정책 등)을 저장하여 추후 분석에 활용합니다.

### D. 트랜잭션 데이터 (`Order`, `TransactionLog`) 개선: 이벤트 소싱 패턴 도입
주문이나 재고 상태는 한 순간의 스냅샷이 아닙니다. '어떤 일이 왜 발생했는지' 기록하는 것이 중요합니다.

*   **추천 방식:** **Event Sourcing Pattern (사건 기반 아키텍처)**
*   `Order` 테이블을 단순한 최종 정보 저장소가 아닌, `Order_Events`와 같은 이벤트 로그의 집합으로 설계하는 것을 고려해야 합니다.

| 이벤트 예시 | 발생 시점 | 기록 내용 | 중요성 |
| :--- | :--- | :--- | :--- |
| `ORDER_CREATED` | 주문 접수 시 | 초기 결제 금액, 고객 정보 | 트랜잭션 시작점 |
| `PRICE_UPDATED` | 가격 정책 변경 시 | 이전가/신가격, 변경 사유 | 수익성 추적의 핵심 |
| `INVENTORY_ADJUSTED` | 재고 변동 발생 시 | 증감 수량, 원인 (판매/반품/입고) | 실시간 판매 관리 |

## 3. 요약 및 개발팀 참고 지침

1.  **데이터 무결성 우선:** 가장 중요한 것은 데이터의 '진실성'입니다. `Order`와 `PricingRule`은 단순한 관계가 아닌, **시간 축을 가진 버전 관리 시스템**으로 설계해야 합니다.
2.  **유연성과 확장성 확보:** 모든 외부 소스(Agent)의 비정형 데이터는 `JSONB` 타입을 활용하여 임시 저장소처럼 사용하고, 핵심적인 속성만 정규화된 컬럼에 매핑하세요.
3.  **Performance 최적화:** 트래픽이 폭증하는 로그(`TransactionLog`)나 대량의 상태 변화가 발생하는 테이블은 인덱싱 전략(특히 B-Tree와 GiST)을 사전에 설계해야 합니다.
