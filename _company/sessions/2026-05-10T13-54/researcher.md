### 1. 기술 스택 학습 로드맵 비교 분석

구매대행 통합 솔루션은 외부 API 연동(통신), 데이터 처리(파이프라인), 비즈니스 로직 구현(백엔드), 그리고 사용자 인터페이스(프론트엔드)를 포괄합니다. 최신 모범 사례는 **"빠른 프로토타입 구축"**과 **"시스템 안정성 확보"**라는 두 가지 축을 중심으로 구성되어야 합니다.

| 학습 목표 영역 | 전통적 접근 (Legacy/Monolithic) | 최신 모범 사례 (Modern/Microservices) | 권장 학습 우선순위 |
| :--- | :--- | :--- | :--- |
| **핵심 언어/프레임워크** | Python (Django/Flask) 또는 PHP 기반의 단일 시스템 구축 | **Python (FastAPI/Django)** + 비동기 처리(Asyncio) 기반 마이크로서비스 아키텍처(MSA) | 1순위: Python 비동기 프로그래밍, API 설계 심화 |
| **데이터베이스** | 관계형 DB (MySQL, PostgreSQL) 단독 사용 | **Polyglot Persistence:** 트랜잭션 데이터는 RDB (PostgreSQL), 로그/캐싱은 NoSQL (Redis, MongoDB) 혼합 사용 | 2순위: RDB 정규화 및 NoSQL 데이터 모델 이해 |
| **API 연동** | RESTful API의 단순 호출 중심 | **GraphQL 또는 Event-Driven Architecture (EDA):** 비동기 이벤트 기반 통신(Kafka/RabbitMQ)을 통한 시스템 간 결합도 낮추기 | 3순위: OAuth2/JWT 인증 및 메시지 큐 설계 |
| **배포/인프라** | 자체 서버 구축 및 관리 | **컨테이너화 (Docker) + 오케스트레이션 (Kubernetes):** CI/CD 파이프라인 자동화 | 4순위: Docker, 기본적인 Kubernetes 개념 이해 |

#### 💡 분석 요약 및 제언
1.  **통합 솔루션의 핵심:** 통합 솔루션은 다양한 외부 API(쿠팡)와 내부 데이터를 안정적으로 연결해야 하므로, **비동기 통신(EDA)**과 **마이크로서비스 아키텍처(MSA)** 개념을 초기부터 학습하는 것이 장기적인 확장성과 안정성에 유리합니다.
2.  **학습 우선순위:** 당장 구현에 필요한 것은 **Python 기반의 API 서버 구축 능력**과 **데이터베이스 스키마 설계 역량**입니다. 이후 시스템 확장을 위해 MSA 및 메시지 큐 지식을 병행 학습해야 합니다.

### 2. 데이터 모델 설계 최신 모범 사례 비교 분석

데이터 모델은 시스템이 데이터를 얼마나 효율적으로 저장하고, 트랜잭션의 무결성을 보장하는지를 결정합니다. 통합 솔루션에서는 **'트랜잭션 안정성'**과 **'데이터 유연성'**을 동시에 확보해야 합니다.

| 설계 원칙 | 관계형 데이터베이스 (RDB) 기반 접근 | NoSQL/스키마리스 접근 | 통합 솔루션에 대한 적용 방안 |
| :--- | :--- | :--- | :--- |
| **정규화 수준** | 3차 정규형(3NF) 이상을 목표로, 데이터 중복 최소화 및 무결성 극대화. | 스키마 유연성을 확보하며, 관계를 애플리케이션 레벨에서 관리. | **하이브리드 접근:** 핵심 트랜잭션(주문, 재고)은 RDB로, 로그, 사용자 피드백 등 비정형 데이터는 NoSQL로 분리하여 저장. |
| **관계 정의** | 명시적인 외래 키(Foreign Key)를 사용하여 테이블 간의 엄격한 관계를 정의. | 임베딩(Embedding) 또는 참조(Reference) 방식을 사용하며, 쿼리 시점에 관계를 추론. | **중요 트랜잭션은 RDB로 고정**하고, 외부 API 데이터나 로그는 JSON 형태(NoSQL)로 저장하여 유연성을 확보. |
| **트랜잭션 안정성** | ACID 원칙을 보장하여 금융/재고 거래의 정확성 보장. | 분산 트랜잭션 처리가 복잡해지므로, 서비스 단위로 트랜잭션을 격리하는 방식 채택. | **핵심 데이터(주문 상태, 재고)는 RDB 내에서 ACID를 유지**하고, API 연동 데이터는 별도의 로그 테이블에 기록하여 이관 실패 시에도 시스템의 핵심 안정성을 보장. |

#### 💡 분석 요약 및 제언
1.  **모델 설계 전략:** 통합 솔루션은 **'핵심 비즈니스 로직(주문/재고)'을 RDB로 확고히 하고, '외부 연동 데이터(API 응답), 시스템 로그'는 NoSQL로 유연하게 관리하는 하이브리드 모델**이 가장 적합합니다.
2.  **데이터 흐름:** 쿠팡 API에서 들어오는 데이터는 시스템 내부의 **정규화된 데이터 모델에 맞춰 변환 및 매핑(Mapping)** 과정을 거쳐 저장되어야 합니다. 이 변환 로직이 솔루션의 핵심 품질을 결정합니다.

### 3. 개발팀 제시 구조화된 계획 (Action Plan)

위 분석을 바탕으로, 개발팀에게 제시할 **MVP(Minimum Viable Product) 기반의 단계별 로드맵**을 제안합니다.

**목표:** 시스템의 안정적인 데이터 구조를 정의하고 핵심 기술 스택을 확정한다.

| Step | 세부 활동 내용 | 산출물 요구 사항 | 담당 에이전트 | 예상 기간 |
| :--- | :--- | :--- | :--- | :--- |
| **1.1** | **기술 스택 최종 확정:** Python/FastAPI, PostgreSQL, Redis 조합을 공식 채택하고 학습 범위 명확화. | 기술 스택 결정 문서 | Developer | 1주 |
| **1.2** | **핵심 데이터 모델 설계 (RDB):** 주문, 상품, 사용자, 재고의 관계를 정의하는 ERD 초안 확정. | 최종 ERD 및 정규화 원칙 문서 | Developer / Researcher | 1주 |
| **1.3** | **API 연동 스펙 구체화:** 쿠팡 API에서 필요한 모든 엔드포인트, 인증 흐름, 데이터 필드를 상세히 정리. | API 명세서 (Request/Response Spec) | Researcher | 1주 |

| Step | 세부 활동 내용 | 산출물 요구 사항 | 담당 에이전트 | 예상 기간 |
| :--- | :--- | :--- | :--- | :--- |
| **2.1** | **데이터 파이프라인 구축:** 쿠팡 API 호출 → 데이터 정제 → RDB 저장의 자동화된 흐름(파이프라인) 구현. | Python 통신 모듈 및 데이터 ETL 로직 코드 | Developer | 2주 |

| Step | 세부 활동 내용 | 산출물 요구 사항 | 담당 에이전트 | 예상 기간 |
